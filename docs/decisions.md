# Decisions

Dated decisions for this repo, newest last.

- 2026-11-22: created from the ops starter kit, area `co-plugins`.
- 2026-11-22: created as a skeleton on our side (for Captive Origins' business accounts). npm name @extantape/payload-plugin-sharing. MIT, EXTANT APE. Contributions from co/ branches; only the owner merges.
- 2026-11-22: first version built for Captive Origins' business accounts, following three Captive Origins rules: shared collections with Owner, Manager and Viewer and at least one Owner; business accounts and brands; and a minor may be in a shared collection only through a family group with a linked guardian. The plugin stays agnostic: the minors rule is the host's `refuseMember` veto, not built in.
- 2026-11-22: invitations start as `invited` and a user accepts their own; organizations accept only through a host `canAccept` hook. Removal is a status, never a delete. The last-Owner rule is enforced in hooks with a lock write to the group inside the request's transaction, so it needs a MongoDB replica set.
- 2026-11-22: a group's kind and first owner are fixed after creation, because host rules (such as the minors rule) can depend on the kind.
- 2026-11-22: after EXTANT APE's review of the positions PR, `refuseMember` is required (`false` opts out), deletes always throw, member changes go to an append-only `share-member-events` history, and Viewers see only Owners and Managers by default (kids come first; `canRead` widens it).
- 2026-11-22: after EXTANT APE's second review: private member fields are Owner and Manager only, organization acceptance goes through `canAccept` and user acceptance is the user alone, organizations are vetoed per person through `peopleOf`, the plugin refuses to run without transactions, and bulk member updates are refused.
- 2026-11-23: after EXTANT APE's third review: `canRead` only adds rows to the default rules; the transactions check opens and rolls back a real transaction (`allowWithoutTransactions` opts out); self-accept and self-leave can't write notes; a removal can't carry a level change. The veto still isn't run when `identities` resolves and isn't given current members: the README says `peopleOf` must cover everyone `identities` maps and that the host queries members itself, because the veto has no group or level to judge at that point.
- 2026-11-23: after the re-review: `identities` keeps an organization only when `peopleOf` lists the user (asked once per request, dropped on a throw), `invitedBy` is always the acting user or none, member changes refuse without a request transaction, and non-staff can't write notes on an organization's row they act for. Someone who joins an organization after it was invited is still not vetoed until acceptance; documented.
- 2026-11-23: the host veto moves from invite to accept (the owner chose to fix the oracle first). Inviting always succeeds for signed-in users, so an inviter can't tell a minor from an adult; a level change on an invited row skips the veto and acceptance decides; a veto refusal of a level change on an active row is the plain 403 a `canChangeLevel` no gives; "already in this group" is said only to someone who can read the row. Server code and a group's founding Owner are still asked on invite.
- 2026-11-23: organizations and level changes. An organization is never refused for a person behind it when a signed-in person founds or accepts for it; it joins and the vetoed person is left out of it for that group (owner: "Quietly leave the minor out (Recommended)"). A level-dependent veto can be told apart by an Owner on active rows, and that is documented, not hidden (owner: "Document it for now (Recommended)"). `refuseMember` is a function or exactly `false`.
- 2026-11-23: after the fourth review: a level change on an active organization row quietly leaves a newly vetoed person out and goes ahead (the owner's rule for founding, inviting and accepting now covers it), `peopleOf` is a function or exactly `false`, and the left-out list stays out of audit payloads. The exclusion is decided at join time and not re-checked, documented for a late joiner, a minor who turns adult and an adult who later becomes vetoed.
- 2026-11-27: duplicating is off for all three sharing collections, for everyone, server code included. A create under access rules must be saved as those rules checked it, or it is rolled back; field names with a dot or a leading `$` are refused. A duplicate of a host record keeps its share group only for an Owner or Manager of that group, the same as a new record.
- 2026-11-27: `shareGroupField` judges a change against the field's own earlier value, so the rule is the same in groups and named tabs. Where a change can't be checked (arrays, blocks, localized values) the plugin refuses to start. A restore or write that can't be judged is refused. Collections that use the field accept only ordinary field names at the top level of a write, server code included.
