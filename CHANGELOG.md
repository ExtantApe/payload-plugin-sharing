# Changelog

## 0.1.1 (2026-11-25)

- A write refused for a missing transaction (the database stopped handing them out, or server code passed `disableTransaction`) now throws a 403 whose data is exactly `{ refusal: 'transactions-required' }`. The message is unchanged. Review tools such as whitehat count only that shape, or a bare 401, 403 or 404, as a refusal, so this guard showed as not checked before. Tested: the `disableTransaction` test now checks the shape (114 in all); it fails on the old code. Not tested: a live site.

## 0.1.0 (2026-11-23)

- Fourth review fixes. A level change on an active organization row now leaves a newly vetoed person out and succeeds, so an Owner gets the same answer whether or not a minor is behind it (before, it was a 403 only when someone was vetoed, and the level could never change). The host's veto of the organization itself is still the plain 403. `peopleOf` must be a function or exactly `false`; `null`, `0`, `''` and `true` stop the plugin from starting. The left-out list is stripped from audit payloads (before and after invite, accept, level change and remove) and from the `member` the host's access hooks are given. README: the left-out list is decided at join time and is not re-checked, with the late joiner, the minor who turns adult and the adult who becomes vetoed spelled out. Tested: 114 tests, including identical status, body, headers and audit at level change with and without a minor behind, the newly vetoed person added with the earlier ones kept, the organization's own refusal still a 403, each bad `peopleOf` value refused, and no left-out list or left-out id in any audit event. Not tested: a live site, and response timing.
- Organizations in sharing: when a signed-in person founds a group for an organization, or accepts for an organization's row, the organization is no longer refused because of a person behind it. It joins, and a person the veto refuses gets no access through it (stored on the row, readable by nobody through the API, and applied wherever access is worked out). The acting person sees the same status, body, headers and audit events (the left-out list is not in them) whoever is behind the organization, and the host's reason is never passed to them. Server code still gets the reasons. `refuseMember` must be a function or exactly `false`; `null`, `0` and an empty string no longer turn the veto off. README: a vetoed member's row stays invited, and with a level-dependent veto an Owner can tell a refused change on an active row from an allowed one. Tested: 109 tests, including the identical-looking result over REST (status, body, headers, audit) for an organization with and without a vetoed person, the same at group founding, no access for the vetoed person (`roleIn`, `groupIdsFor`, `canView`), a person who joined later, a client unable to write the stored list, and the `refuseMember` values. Not tested: a live site, and response timing.
- The veto moves from invite to accept, so an inviter can't learn who it refuses (a minor, say) by inviting them. An invitation always succeeds for a signed-in user and looks the same for everyone; the reason goes to the person accepting. A level change on an invited row doesn't ask it and looks the same for everyone; on an active row a refusal looks like a `canChangeLevel` no, with nothing written and no history row, but an Owner can still tell a refusal from a success (documented). "Already in this group" is said only to someone who can read that row. Server code and a group's founding Owner are still asked on invite and see reasons. Tested: 104 tests, including that an inviter gets the same answer, row and history for a minor and an adult at invite, at level change on invited rows, and on duplicates (on active rows only the refusal's look is tested); the full suite passed 5 runs in a row. Not tested: a live site.
- The two `find` calls that pass the request (the last-Owner check and the duplicate-invite check) no longer paginate, so no count query rides beside them on a transaction's session, which could intermittently fail with NoSuchTransaction. Tested: 101 tests, including one that records every `find` made with a request and requires `pagination: false`; the full suite passed 5 runs in a row. Not tested: a live site.
- The repo, with the standard Payload plugin kit. Public since 2026-11-22.
- The first version of the plugin (for Captive Origins' business accounts):
  - `share-groups` and `share-members` collections, with Owner, Manager and Viewer levels the host can rename, and member types the host can extend to organizations.
  - A group always keeps an active Owner. The last Owner can't leave or be demoted, and two Owners changing each other at once leave one.
  - Host hooks `canCreateGroup`, `canInvite`, `canChangeLevel`, `canRemove` and `canAccept`, all failing closed on anything but an exact `true`.
  - A required `refuseMember` veto (or an explicit `false`) on accept and on level changes of active members (invite too for server code, see below), applied to server code too. The reason is shown to the person refused, so the README warns against reasons that reveal an age.
  - An append-only `share-member-events` history of every invite, accept, level change and removal, written in the same transaction.
  - Second review fixes: `notes`, `invitedBy` and `removedBy` are readable by Owners and Managers only (notes capped at 500); a user accepts only their own invitation and `canAccept` is for organizations; a throwing `identities` hook refuses before any host hook runs; `refuseMember` runs for each person behind an organization (`peopleOf`, required with organizations); the plugin refuses to start without database transactions; bulk member updates are refused.
  - Deletes always throw, even with `overrideAccess`. Hooks receive plain ids and references, and the `id` and `data` of the change. Viewers see only Owners and Managers by default.
  - Audit hooks for invite, accept, change level and remove.
  - `shareGroupField`, `canView`, `canEdit` and `sharedWhere` for host collections.
  - Nothing is deleted; removal is a status, and a unique key stops a second live row for the same group and member.
  - Third review fixes: `canRead` can only add rows to the default rules (`true`, `{}` and a throw add nothing); the transactions check opens and rolls back a real transaction, so an adapter with `transactionOptions: false` is refused, with an `allowWithoutTransactions` opt-out; self-accept and self-leave can't overwrite staff notes; a removal can't carry a level change; accept with a level change records both events; the veto runs before the already-a-member check; `invitedBy` ignores users from other auth collections; `@payloadcms/graphql` pinned. After the re-review: `identities` keeps an organization only when `peopleOf` lists the user (asked once per request, dropped on a throw); `invitedBy` is always the acting user or none; member changes refuse without a request transaction (`disableTransaction`); non-staff can't write notes on an organization's row they act for or on a new invitation; the transaction check awaits the transaction and covers group creation. Documented: `peopleOf` must cover everyone `identities` maps, the veto isn't given current members, and a group's founding owner stays visible.
- Tested: 100 tests against real Payload 3.92 with an in-memory MongoDB replica set, covering each path above, refusals over REST, GraphQL and bulk update, server-code attempts to revive or widen a membership, repeated two-at-once runs for the last-Owner and duplicate-invite rules, a real adapter started with `transactionOptions: false` (refused), the history rows and who can read them, members keyed by collection, what a Viewer sees of other members, and clean-up of the database and server at the end.
- Not tested: a hosted production database, a live site, the admin screens in a browser, and a very large number of members.
